## Abstract

This proposal describes a protocol for sharing block templates (ie,
the next block's predicted transactions) with peers.

## Motivation

The benefits of sharing block templates are:

 * improving the effectiveness of compact block reconstruction,
   particularly for nodes who have a more restrictive transaction relay
   policy than their peers;

 * allowing nodes that have not been online recently to quickly repopulate
   the top of their mempool;

 * providing a way for transactions to slowly propagate amongst nodes that
   will accept the transaction, even when those nodes are effectively
   isolated from each other for normal operation (due to primarily
   peering with nodes that have more restrictive relay policies); and

 * providing a way for transactions that may have dropped out of nodes'
   mempools to be rebroadcast across the network by third parties,
   potentially providing better privacy than if only the nodes directly
   involved in the transaction would rebroadcast it.

## Specification

This introduces four new messages (`gettmplt`, `tmplt`, `gettmplttxn`,
`tmplttxn`).

### Feature negotiation

Nodes that support this protocol advertise it via a [BIP-434][BIP-434]
`feature` message with `featureid` set to `BIN25-2.1` and an empty
`featuredata`. Nodes MUST NOT send `gettmplt`, `tmplt`, `gettmplttxn`,
or `tmplttxn` messages to peers that have not advertised support for
this feature.

### Template generation

Nodes supporting this feature SHOULD regularly generate "block templates".

These are collections of transactions the node believes are suitable for
inclusion within the next two blocks.

The transactions making up the template MUST be valid for block inclusion
-- for example, all unconfirmed parents of a transaction MUST be included
before the transaction, and consensus limits MUST be respected. The
transactions SHOULD be ordered from highest priority to lowest. Priority
will usually be based on feerate, but is ultimately the decision of the
template generator.

The cumulative weight of the transactions making up the template MUST NOT
exceed eight million weight units as defined in [BIP-141][BIP-141]. Note
that this is twice the block weight limit, and does not include the
overhead that assembling those transactions into a block would involve
(header, coinbase and tx count serialization), so as a result, a template
can contain slightly more than two blocks' worth of transactions.

Templates are identified by a hash, which is the sha256 hash of the
concatenation of the current block tip, and the wtxids of the template
transactions.

Note that templates should never include coinbase transactions.

### Compact vector encoding

This protocol uses two compact encodings for vectors of integers:
`CompactIntVec` for signed 32-bit values and `CompactUIntVec` for
unsigned 32-bit values. Both share the same underlying structure,
differing only in whether a sign bit is included.

Each value is encoded into a bitstream as follows:

1. For `CompactIntVec` (signed), the value is split into a sign bit
   and unsigned magnitude. If `v >= 0`, the sign bit is 1 and the
   magnitude is `v`. If `v < 0`, the sign bit is 0 and the magnitude
   is `-(v + 1)` (so -1 has magnitude 0, -2 has magnitude 1, etc.).

2. For `CompactUIntVec` (unsigned), the magnitude is simply `v` and
   there is no sign bit.

3. The magnitude is mapped to a size class `i` (starting at 0)
   and a residual. Size class boundaries grow by a factor of 16:
   class 0 covers magnitude 0, class 1 covers 1-16, class 2 covers
   17-272, class 3 covers 273-4368, etc.

4. The encoding is: `i` zero bits, followed by a 1 bit, followed by
   the sign bit (for `CompactIntVec` only), followed by `i * 4` bits
   of residual value.

| Prefix zeros | Value bits | Magnitude range      | Bits (signed) | Bits (unsigned) |
| ------------ | ---------- | -------------------- | ------------- | --------------- |
| 0            | 0          | 0                    | 2             | 1               |
| 1            | 4          | 1-16                 | 7             | 6               |
| 2            | 8          | 17-272               | 12            | 11              |
| 3            | 12         | 273-4368             | 17            | 16              |
| 4            | 16         | 4369-69904           | 22            | 21              |
| 5            | 20         | 69905-1118480        | 27            | 26              |
| 6            | 24         | 1118481-17895696     | 32            | 31              |
| 7            | 28         | 17895697-286331152   | 37            | 36              |
| 8            | 32         | 286331153-4581298448 | 42            | 41              |

The stream is terminated by 9 consecutive zero bits (allowing for
coverage of the full range of both `int32_t` and `uint32_t`), with an
additional 0-7 zero bits of padding to reach the next byte boundary.
Decoders SHOULD reject streams with non-zero padding bits.

### `gettmplt`

The `gettmplt` message is defined as a message with the ASCII message type
`gettmplt` and a payload of:

| Type     | Name     | Description |
| -------- | -------- | ----------- |
| uint256  | `basis`  | Hash of a template previously received over this connection to use as delta base (optional)

A `gettmplt` message MAY be sent at any time after a `verack` message has
been received, provided the peer has advertised support for this feature.

Upon receipt of a `gettmplt` message, a node SHOULD reply with a
`tmplt` message.

Supplying a `basis` allows the `tmplt` response to be encoded as a delta
between the old template and the new template, so should be provided
when possible. If a `basis` cannot be provided, the payload for the
message is empty.

If a node receives this message when it had not finished responding to a
previous `gettmplttxn` message, a node MAY finish sending the `tmplttxn`
messages prior to sending the `tmplt` response, but MUST NOT send any
further `tmplttxn` for an old request after sending the `tmplt` response.

### `tmplt`

The `tmplt` message is defined as a message with the ASCII message type
`tmplt` and a payload of:

| Type              | Name       | Description |
| ----------------- | ---------- | ----------- |
| uint256           | `template` | Template hash |
| uint256           | `tip`      | Hash of the current tip used to generate the template |
| uint64            | `nonce`    | A nonce for use in short-ID calculations |
| uint256           | `basis`    | Hash of the template used as delta base, or all zeros |
| CompactIntVec     | `delta`    | Delta-encoded short ID list (if `basis` was not all zeroes) |
| 6 byte integer[]  | `shortids` | 6-byte short IDs |

A `tmplt` message MUST only be sent in response to a `gettmplt` message.

The `tip` field MUST be the block tip at the time the template was built.
Nodes receiving `tmplt` messages MAY use the `tip` value to skip
processing of templates that are outdated or would not connect.

The `basis` entry MUST either match the `basis` parameter from the `gettmplt`
message, or, in the case where the `basis` parameter was not provided or the
hash was not recognised, be all zeroes.

If `basis` is all zeros, the `delta` field MUST be omitted, and the `shortids` field
MUST contain one entry per transaction in the template.

If `basis` is non-zero, the `delta` field MUST be provided as a `CompactIntVec`
representing the delta from the template with that hash.

#### Short transaction IDs

Short transaction IDs are used to represent a transaction without sending
a full 256-bit hash. They are calculated similarly to [BIP-152][BIP-152],
namely by:

 * Concatenating the template and the nonce (in little-endian)
 * Running SipHash-2-4 with the input being the transaction ID (wtxid)
   and the keys (k0/k1) set to the first two little-endian 64-bit integers
   from the above hash, respectively.
 * Dropping the 2 most significant bytes from the SipHash output to make it 6 bytes.

#### Constructing `delta` and `shortids`

The procedure for constructing the `tmplt` payload is:

```python
shortids = []
delta = []
offset = 0
missed_run = 0
for tx in template_txs:
    b = basis_txs.find(tx)
    if b is None or b == offset - 1:
        # b == offset - 1 implies a repeated transaction, should never happen
        shortids.append(get_shortid(tx))
        missed_run += 1
    else:
        while missed_run > 0:
            delta.append(-1)
            missed_run -= 1
        delta.append(b - offset)
        offset = b + 1
```

The `tmplt` payload MAY be cached and reused for different connections that provide the
same basis template.

#### Reconstructing the template `delta` and `shortids`

Processing a `tmplt` message requires building up both a list of transactions in the template,
and a list of the indexes of any missing transactions. This can be achieved as follows:

```python
template = []
missing_diffs = []

delta_offset = 0
basis_offset = 0
shortid_offset = 0
missing_offset = 0
while True:
    if delta_offset < len(delta):
        v = delta[delta_offset]
        delta_offset += 1
    elif shortid_offset < len(shortids):
        v = -1
    else:
        break
    if v == -1:
        assert shortid_offset < len(shortids), "not enough shortids provided; cannot decode template"
        tx = mempool.find_by_shortid(nonce, shortids[shortid_offset])
        shortid_offset += 1
        if tx is None:
            missing_diffs.append(len(template) - missing_offset)
            template.append(None)
            missing_offset = len(template)
        else:
            template.append(tx)
    else:
        assert 0 <= basis_offset + v < len(basis), "basis offset is out of range; cannot decode template"
        template.append(basis[basis_offset + v])
        basis_offset += v + 1
```

If `missing_diffs` is non-empty, a `gettmplttxn` message should be sent
with the `missing_diffs` encoded as a `CompactUIntVec` to recover the
missing transactions.

#### `delta` format

The `delta` format encodes which transactions to select from `basis` in
the new template. For example, if the basis had transactions `[1, 2, 3,
4, 5]` and the new template replaces transaction 3 with a new transaction
6 that CPFPs transaction 5, resulting in `[1, 5, 6, 2, 4]` the `delta`
encoding would be `[0, 3, -1, -4, 1]`.  The "0" indicates the first tx
is exactly as expected, the "3" indicates we're skipping forward, the
"-1" indicates we have a new transaction, "-4' indicates we're skipping
backwards to get txs we skipped over, and the "1" indicates we're skipping
forward again (past the missing tx 3).

### `gettmplttxn`

The `gettmplttxn` message is defined as a message with the ASCII message
type `gettmplttxn` and a payload of:

| Type           | Name       | Description |
| -------------- | ---------- | ----------- |
| uint256        | `template` | Template hash (from `tmplt` message) |
| CompactUIntVec | `indexes`  | Differentially encoded positions of missing transactions |

The `indexes` field is a `CompactUIntVec`, differentially encoded: the
first value is the index in the template of the first missing transaction,
and each value after that is the gap from the previous requested index
to the next, minus one. That is, consecutive indexes (eg, 5 then 6)
encode as 0, a gap of two (eg, 5 then 7) encodes as 1, etc.

A `gettmplttxn` message MAY be sent after receiving a `tmplt`
message to request transactions that the receiver could not
reconstruct from its mempool.

Upon receipt, the sender of the original `tmplt` message SHOULD respond
with one or more `tmplttxn` messages providing the requested transactions.

### `tmplttxn`

The `tmplttxn` message is defined as a message with the ASCII message
type `tmplttxn` and a payload of:

| Type           | Name           | Description |
| -------------- | -------------- | ----------- |
| uint256        | `template`     | Template hash (from `tmplt` message) |
| CTransaction[] | `transactions` | Requested transactions, with witness data |

The transactions are serialized in the same manner as
`BlockTransactions` in [BIP-152][BIP-152].

Transactions requested via `gettmplttxn` are provided via `tmplttxn`
messages.  A single `gettmplttxn` request MAY be answered by multiple
`tmplttxn` messages. Each `tmplttxn` message MUST be limited to under
4MB in size, and SHOULD be limited further, to better allow interleaving
with higher-priority traffic such as block relay.

Transactions in `tmplttxn` messages are provided in the same order
as they were requested in `gettmplttxn`, including when split across
multiple response messages.

The provider SHOULD be able to respond to `gettmplttxn` requests for
a moderate amount of time after sending a `tmplt` message (eg, two
minutes).

 * What happens if the peer doesn't respond?
   - If you send `gettmplt` or `gettmplttxn`, the peer might not
     respond. If so, that's fine, just send a new `gettmplt` at the same
     time you would have if they did respond.
   - A peer not responding should not cause very old templates to
     stick around in memory -- if you don't get a new template from a
     peer, you should still expire its old template(s).
 * Upon template reconstruction
   - Check the reconstructed template hashes to the correct value
     - If not? Could not worry and use as is. -- templates are just
       advisory. Could discard to save memory. Could request a new
       template from that peer immediately.
   - Consider adding the txs to your mempool if they're not already there.
 * How frequently to request gettmplt?
   - Every couple of minutes from a small subset of nodes (eg, all 8 outbounds plus a selection of 8 inbounds)
 * How frequently to generate templates?
   - Generating a template is somewhat expensive, so should not be done immediately in response to requests.
   - One approach is to generate templates on a timer, eg averaging every 30 seconds.
   - When a `gettmplt` request comes in, responding with either the most recent template, or deferring the
     response until a new template is generated is possible.
   - Deferring and sending a fresh template is generally superior,
     as this avoids sending txs that have recently been RBFed, or sending
     a template that is based on an old block if a new tip has just
     been announced.
 * Delta vs shortids?
   - Every "-1" entry in delta consumes a shortid. If there are additional
   shortids after processing delta, they are treated as if there was
   an additional series of "-1" entries at the end of delta that would
   consume all the extra shortids. This makes it slightly more efficient
   when a set of new txs are included at the very end of the template.
 * What happens with shortid collisions?
   - If the collision is detected (you have two matches in your mempool), just request the tx
   - If the collision is undetected, you will construct the wrong
     template, detectable by comparing against the expected template
     hash. Discard the template, and request a new template at the
     usual schedule.
 * Nonce selection
   - Nonces should be randomly chosen per template, so that a random
     shortid collision doesn't repeat indefinitely.
   - Choosing different nonces for the same template when advertising on
     different interfaces (eg ipv4 vs tor) may be a privacy benefit,
     however other avenues for determining those two interfaces belong
     to the same node may still exist.
 * Comparing template txs to your mempool
   - When you receive a template you SHOULD attempt to include transactions in your
     mempool, just as if you'd received them via INV/GETDATA/TX messages.
   - If txs conflict or fail policy checks, that's fine: leave them out
     of your mempool, but use the templates to resolve any compact block
     announcements, in case the next block's miner doesn't share your
     mempool policy and does include the tx.
   - Don't attempt to add txs to your mempool too frequently; if they reject once,
     they'll likely reject again until something else changes.
 * Invalid transactions
   - If a peer includes consensus-invalid transactions in its template,
     a node MAY disconnect that peer.
   - Detecting consensus-invalid transactions can be costly, so it is not
     required or recommended that nodes do this.
   - Nodes may choose to check a random sampling of txs that fail mempool
     acceptance against consensus rules in order to reduce the cost of
     performing these checks.
 * Single SHA256
   - Nothing here needs more than a checksum, so using sha256d is just
     a waste of cycles.
 * Privacy
   - This protocol reveals the top of your mempool to your peers.
   - If you are prioritising some transactions, this will reveal that
     prioritisation (unless the prioritisation has no effect, or does
     not push the tx into the top of the mempool).
   - If you have unusual mempool acceptance rules, this may reveal that fact.
   - Including recent transactions in your templates will reveal that
     you have just received those transactions to your peers, however
     so will announcing those transactions via INV message. Template
     generation SHOULD be synchronised with INV message timing to minimise
     the information leaked here.
   - However, provided you have a similar set of transactions in your
     mempool to your peers, and use a similar prioritisation mechanism,
     your templates will largely match your peers, so will not be a
     privacy leak.
 * Interaction with block-relay-only connections
   - Repeatedly sharing templates with block-relay-only connections can provide
     a path for txs to enter your mempool via the block-relay-only
     connection, which may be able to be used by attackers to discern
     the existence of that connection.
   - If templates are shared over a block-relay-only connection, they
     should therefore only be shared once, when the connection is first
     initiated.

### Protocol design

This design provides a negotiation mechanism, the ability for
a peer to request template data, delta-encoded template updates,
and chunked retrieval of missing transactions.

The delta encoding allows efficient updates when successive templates
share most transactions in roughly the same order, which is the common
case (templates are ordered by fee rate, and most transactions persist
across updates).

### Template size

This BIP specifies a maximum template size equivalent to two blocks'
worth of transactions. This is chosen so that even if two blocks are
mined in quick succession, prior templates that were shared using this
protocol are likely to have included the transactions from both blocks.

If blocks are found randomly, it is expected that 5% of blocks will
be found within 30 seconds of the previous block, which is about 7 per
day; so this seems frequent enough to address explicitly. In contrast,
the chances of finding two blocks within 30 seconds of a block is only
0.12%, so even in ideal circumstances, is only expected to occur about
once per week, and thus further optimisation does not seem warranted.

### Chunked transaction retrieval

Template transactions are retrieved via dedicated `gettmplttxn`/`tmplttxn`
messages rather than reusing [BIP-152][BIP-152] `getblocktxn`/`blocktxn`.
This avoids the 4MB p2p message size limit (which could be exceeded when
requesting two blocks' worth of transactions with an empty mempool) and
keeps template transactions on a separate path from normal relay, since
they may include transactions that violate the receiver's local policy.

Response messages are limited to avoid
introducing latency on higher-priority messages such as block
announcements. The provider streams chunks as it is able, without
the receiver needing to send multiple requests.

### Compact vector encoding

The encoding is optimized for sequences of small values. For the template
delta use case (`CompactIntVec`), the most common values are expected
to be 0 (next predicted item matches) and -1 (insert a new transaction),
which are both encoded in just 2 bits. Less common operations (reordering,
skipping removed transactions) encode in 7-22 bits, which is still
significantly cheaper than transmitting a full 6-byte short ID (48 bits).
The unsigned variant (`CompactUIntVec`) saves one bit per entry and is
used for `gettmplttxn` indexes where only non-negative values are needed.

### Template hash

The template hash (SHA256 of concatenated tip and wtxids) serves three
purposes: error detection (the receiver can verify the reconstructed
template), template identification (for `gettmplttxn` requests), and as
the delta basis reference for future template updates.

### Delta basis always from sending peer

While the sender of `gettmplt` is able to specify the basis hash, they
are expected to only specify hashes of templates previously sent by that
specific peer.  This allows that peer to cache how the transactions from
the basis were rearranged to achieve the newer template, which can be
an expensive operation. This also ensures that the basis template cannot
be chosen adversarially.

### Continuation during new blocks

When a new block is found while template transactions are being
streamed, the provider should continue streaming rather than aborting.
The tail of the template (the second block's worth of transactions)
contains exactly the transactions likely to appear in the next block.
Additionally, the receiver needs a fully reconstructed template to
serve as the delta basis for subsequent template updates.

## Recommendations

To be advised.

Care should be taken regarding efficiency and privacy concerns when
implementing or deploying this protocol.

## Backward compatibility

This protocol uses [BIP-434][BIP-434] feature negotiation, so clients that
specify a protocol version older than 70017 will not see any messages
related to this feature, and clients that implement BIP-434 but do not
support this feature will only see the feature announcement message,
which BIP-434 requires they accept and ignore.
