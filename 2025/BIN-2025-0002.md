## Abstract

This proposal describes an efficient protocol for sharing block templates
(ie, the transaction a node predicts will be included in the next block)
with peers.

## Motivation

The benefits of sharing block templates include:

 * improving the effectiveness of compact block reconstruction,
   particularly for nodes who have a more restrictive transaction relay
   policy than their peers;

 * allowing nodes that have not been online recently to quickly repopulate
   the top of their mempool;

 * providing a way for transactions to slowly propagate amongst nodes that
   will accept the transaction, even when those nodes are effectively
   isolated from each other for normal operation (due to primarily
   peering with nodes that have more restrictive relay policies); and

 * providing a way for transactions that may have dropped out of nodes'
   mempools to be rebroadcast across the network by third parties,
   potentially providing better privacy than if only the nodes directly
   involved in the transaction would rebroadcast it.

Sharing such templates efficiently allows nodes to gain those benefits
automatically.

## Concepts

### Template

 * Collection of txs
 * Unordered
 * 8M weight limit (two blocks)
 * Txs should be valid as at the tip (consensus valid, non-conflicting, no missing deps)
 * Txs do not need to comply with policy rules
 * Identified by template hash based on the current block tip and the txs in the template

### Shortids

 * Short randomized identifier for txs in a template
 * Randomized; seed chosen per template by the template generator
 * Similar approach as compact blocks
 * If you already have the tx (in your mempool, from another template) it's
   cheap to match the shortid and find the tx.
 * Provides the tx ordering necessary for generating the template hash.

### Shortid Reconciliation Overview

 * The use of shortids already gives us a relatively compact way of describing
   templates -- 92kB for 16000 txs, eg.
 * However we can do better:
    - sequential templates are often very similar
    - the receiving and generating node will often generate very similar templates
 * We use the previous template as a basis for specifying the new template
 * And we use minisketch to enable efficient set-reconciliation of the missing
   txs.
 * This will give the receiver a complete list of all the shortids for
   all transactions in the template.

### Transaction Sync

 * Shortid reconciliation will allow you to build up a skeleton of the template
   based on all the transactions you have, but some transactions may be missing.
 * We request these missing transactions from the peer, identifying them
   by position in the template. We use the shortid values to determine
   the positioning in the template.

### Template Validation

 * Once we have all the txs for the template, we calculate the template hash
 * If this does not match the template hash presented by our peer,
   we reject the template (either we were given bad data, or we had an
   undetected shortid collision)

### Template Failure

 * Template sharing is non-essential, so failures can be dealt with in a variety of ways:
    - preserve whatever new txs were obtained and process them as normal
    - ignore the failure and retry later
    - disconnect (or ban) the peer for protocol violation

## Specification

### Protocol Flow

Obtaining a peer's template consists of four major phases:

 * Requesting a new template (round 0 `gettmplt`, `tmplt`)
 * Reconciling the template shortids (round 1..4 `gettmplt`, `tmplt`)
 * Resolving the shortids against the mempool and other templates
 * Obtaining missing transactions (`gettmplttxn`, `tmplttxn`)

### Messages

#### The `gettmplt` message

The payload of the `gettmplt` message contains the following data for round 0:

| Type        | Name         | Description |
| ----------- | ------------ | ----------- |
| `uint8_t`   | `round`      | Round identifier (0) |
| `uint256`   | `basis_hash` | Hash of previous template from this peer to use as a basis (optional) |

The payload of the `gettmplt` message contains the following data for rounds 1-4:

| Type        | Name           | Description |
| ----------- | -------------- | ----------- |
| `uint8_t`   | `round`        | Round identifier (1, 2, 3, or 4) |
| `uint256`   | `hash`         | Hash of the template |
| `uint32_t`  | `shortid_mask` | Groups to send shortids for |
| `uint32_t`  | `sketch_mask`  | Groups to send sketches for |

A `gettmplt` message with `round` greater than zero MUST NOT be sent
except in response to `tmplt` message for the same template hash for
the immediately prior round.

For round 4, `sketch_mask` MUST be zero.

#### The `tmplt` message

The payload of the `tmplt` message contains the following data for round 0:

| Type          | Name          | Description |
| ------------- | ------------- | ----------- |
| `uint256`     | `hash`        | Hash of the template |
| `uint8_t`     | `round`       | Round identifier (0) |
| `uint256`     | `tip_hash`    | Block hash of the tip at the time the template was generated |
| `nonce`       | `uint64_t`    | Template-level nonce for shortid computation |
| `uint256`     | `basis_hash`  | Hash of the basis specified in the `gettmplt` message, or 0 |
| byte-vector   | `basis_delta` | GR-encoded positions of transactions retained from the basis template |
| sketch-vector | `sketches`    | Four stride-4 sketches of transactions in the template |

The payload of the `gettmplt` message contains the following data for rounds 1-4:

| Type          | Name           | Description |
| ------------- | -------------- | ----------- |
| `uint256`     | `hash`         | Hash of the template |
| `uint8_t`     | `round`        | Round identifier (0) |
| `uint32_t`    | `shortid_mask` | Groups to send shortids for |
| `uint32_t`    | `sketch_mask`  | Groups to send sketches for |
| byte-vector   | `shortids`     | GR-encoded deltas of shortids in requested groups |
| sketch-vector | `sketches`     | Requested additional sketches of transactions in the template |

## Backward Compatibility

This protocol uses [BIP-434][BIP-434] feature negotiation, so clients that
specify a protocol version older than 70017 will not see any messages
related to this feature, and clients that implement BIP-434 but do not
support this feature will only see the feature announcement message,
which BIP-434 requires they accept and ignore.
